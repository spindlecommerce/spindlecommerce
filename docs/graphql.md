# GraphQL API design

One Pothos schema definition produces two APIs:

| Endpoint | Audience | Authentication |
|---|---|---|
| `POST/GET /graphql` | Storefronts and apps | Anonymous, or a customer access token (`Authorization: Bearer …`) |
| `POST /admin/graphql` | Back office and integrations | Staff access token, or an API key (`Authorization: Bearer ek_…`) |

Shared types (`Product`, `Money`, `Order`, …) are defined once. Admin-only fields, such as a product's cost or a customer's internal notes, exist only in the admin sub-graph, so storefront introspection never reveals them. The generated SDL is checked in at [`../schema/storefront.graphql`](../schema/storefront.graphql) and [`../schema/admin.graphql`](../schema/admin.graphql).

## Conventions

1. **Global object identification.** Every entity implements `Node` with an opaque `id`, written `gid://ecom/<Type>/<uuid>`. `node(id:)` and `nodes(ids:)` refetch anything.
2. **Cursor connections.** Unbounded lists are Relay connections (`first`/`after`) with `pageInfo` and `totalCount`. Entity lists use keyset cursors on time-ordered ids, which stay stable under concurrent writes. Relevance-ranked search uses opaque offset cursors, capped at 10,000 results. The product connection also returns `facets` (disjunctive) and `priceRange`. Backward paging (`last`/`before`) is rejected with a typed error.
3. **Money is `{ amount: Decimal!, currencyCode: CurrencyCode!, formatted: String! }`.** `Decimal` is a string scalar such as `"19.99"`, produced from integer minor units.
4. **Context is part of the operation.** `@inContext(channel:, locale:, currency:)` on the operation sets the channel, locale and currency, so tooling and GET caching see it. The `X-Channel`, `Accept-Language` and `X-Currency` headers are fallbacks.
5. **Mutations are `<entity><Action>`**, e.g. `cartLinesAdd` or `productCreate`. Each takes one `input` (or a few named arguments) and returns a payload union: `<Mutation>Success` or a typed error.
6. **Errors are data.** Expected failures are object types implementing `Error { message, code }`: `ValidationError` (with `fieldErrors[{ path, message }]`), `NotFoundError`, `InsufficientStockError`, `CouponNotApplicableError`, `AuthenticationError`, `PermissionDeniedError`, `CartNotReadyError` and others. The top-level `errors` array is kept for bugs and limit violations.
7. **Checkout without steps, and idempotent.** `cartUpdate(cartId, input)` takes any checkout details in one call, in any order: email, addresses (complete or not), shipping and payment methods. Shipping rates and tax are priced from the address once it has a postal code. The cheapest rate is selected until the shopper chooses one, and a chosen rate is never swapped for another. The billing address is the shipping address unless the cart has its own. `cartUpdate` also moves the cart to another of its channel's currencies and languages (`currencyCode`, `locale`), as a language and currency picker does. The lines are priced again and named in the new language, and a chosen shipping or payment method that the new currency does not offer is dropped, so the cheapest rate is selected again. `checkoutPlaceOrder(cartId, idempotencyKey, input)` can save the details and place the order in the same call. Every problem is reported at once (`ValidationError.fieldErrors`, `CartNotReadyError.fieldErrors`), and retrying with the same key returns the same order.
8. **Evolve, don't rename.** Fields are added, and deprecated with `@deprecated(reason:)`. Nothing is named `…V2`.
9. **Typed scalars:** `DateTime`, `Decimal`, `CurrencyCode`, `CountryCode`, `LocaleCode`, `EmailAddress`, `JSON`.

## Performance and safety

- **N+1 prevention.** Request-scoped DataLoaders (`src/graphql/loaders.ts`) batch every relation: variants by product, prices by variant, salable quantity by variant, translations, categories, media, and order lines and documents. One loader caches the priced cart quote per request, and cart mutations clear it.
- **Query cost.** The complexity plugin gives every field a cost, and lists multiply by `first`. Requests above a depth of 12, 250 selections in all, or a complexity of 2,000 are rejected. Depth and complexity are configurable, and admin operations get a higher complexity budget.
- **Persisted operations.** Production storefronts can be restricted to an allowlist of operation hashes with Yoga's persisted-operations plugin.
- **Introspection** is off by default in production (`GRAPHQL_INTROSPECTION`). Unexpected errors are masked there too. Expected domain errors outside a result union keep their `extensions.code`, and invalid credentials return HTTP 401.

## Caching

Public storefront fields (catalog, categories, content, route) are cached per `(operation, variables, channel, locale, currency, customer group)`. Private fields (`cart`, `me`, orders) mark the response as private and uncacheable. When a product, price, stock level or category changes, the outbox worker invalidates cached results by entity id. Cache scopes are explicit in the schema.

## Subscriptions

`orderUpdated(orderId:)` streams a signed-in customer's order changes over Server-Sent Events (GraphQL over SSE, `Accept: text/event-stream`). The outbox worker feeds it, so subscribers see only committed state. Each update carries `status`, `paymentStatus` and `fulfillmentStatus` as snapshotted when its event was written, plus `order` for the current state. `pnpm e2e` prints a live stream:

```
order.placed → OPEN/PENDING/UNFULFILLED
order.payment_authorized → OPEN/AUTHORIZED/UNFULFILLED
order.payment_captured → OPEN/PAID/UNFULFILLED
order.fulfilled → OPEN/PAID/FULFILLED
order.completed → COMPLETED/PAID/FULFILLED
order.refunded → COMPLETED/PARTIALLY_REFUNDED/FULFILLED
```

## Storefront operations

| Task | Operations |
|---|---|
| Search and browse products | `products(query, filter, sort, first, after)` → connection with `facets`, `priceRange`, `totalCount` |
| Categories | `category(id \| slug)`, `categoryTree` |
| Resolve a URL | `route(path)` → `Page \| Product \| Category \| Redirect` |
| Start a cart | `cartCreate(input)` → `Cart` |
| Add to cart | `cartLinesAdd(cartId, lines)` |
| Checkout details | `cartUpdate(cartId, input)`. `cartShippingAddressSet` and the other single-detail mutations remain, deprecated. |
| Coupons | `cartCouponApply` / `cartCouponRemove` (several coupons per cart) |
| Place the order | `checkoutPlaceOrder(cartId, idempotencyKey, input)` |
| Sign in and out | `customerLogin` → access and refresh token pair; `tokenRefresh`, `logout` |
| Accounts | `customerRegister`, `customerUpdate` |
| Delete an address | `customerAddressDelete(id)` → payload with `deletedId` |
| Order history | `me.orders(first, after, status)` |
| Find a guest's order | `guestOrder(number, email, postalCode)` |
| Cancel an order | `orderCancel(orderId, reason)`, shared by both APIs |
| The shopper's cart | `me.activeCart`, `cart(id: ID!)` |

The admin API covers catalog, pricing, inventory, customers, orders (capture, fulfil, refund, cancel), promotions, tax, shipping, payments, content, webhooks, staff and API keys.
